# Synchronization receipts and manual field merges

Each `change_id` identifies one exact sync request across the whole server. A retry with the same user, project and canonical payload replays the stored outcome without applying another write. Reusing the ID for a different request returns `change_id_payload_mismatch`; using it in a different scope returns `change_id_in_use`. Neither case exposes another project's receipt. Transient failures without a persisted receipt can retry using the original ID. SQLite reserves the writer before reading receipts; PostgreSQL serializes the receipt IDs inside the transaction, including requests for different projects.

Apply Alembic revision `0003` before starting the updated server against an existing database. It adds `payload_hash` to `sync_receipts`. Older receipts cannot be verified because their request payload was not stored; a retry of one returns `receipt_unverifiable`. Such changes need a new change ID and, when necessary, a refreshed base version. New rows retain their hash with the outcome. The superuser-only project maintenance endpoint prunes audit logs at `days` (default `RETENTION_DAYS`) but retains sync receipts for at least `SYNC_RECEIPT_RETENTION_DAYS` (default 365 days). Idempotent replays are guaranteed only while the receipt is retained; operators should set the window longer than their maximum offline retry horizon.

Select a conflict in the Conflict Center, then choose **Merge fields…** to open a separate dialog. Each differing editable field appears alongside the local and saved server values. Choose **Mine** for at least one field, leave the others on **Server**, then select **Queue merge**. **Cancel** keeps the conflict unresolved. The merge does not infer a three-way merge: the outbox stores no common ancestor. Identity, parent relationships, automatic timestamps, version and derived score fields are never selectable; editable dates such as `identified_at` can be selected. Deletions must use the existing explicit resolution choices. For scored items, impact comes from the selected dimension values when any dimensions are populated.

Resolving a merge atomically replaces the blocked outbox row, applies the saved server copy locally, applies the chosen fields, and queues a new upsert with a new change ID and the exact saved server version. The pull watermark is rewound so newer server edits can be fetched. If the server changed again, optimistic version checking returns another conflict instead of silently overwriting that change. A local copy newer than the saved server snapshot is rejected for manual refresh before merging.
